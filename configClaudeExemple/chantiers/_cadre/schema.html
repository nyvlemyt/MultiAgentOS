BDF GESTION / EVE

Le socle de données ESG et financières de BDF Gestion

EVE reçoit les fichiers de 8 fournisseurs de données extra-financières (JUMP, ISS, IDL, S&P, Trucost, CDC Biodiversité, MSCI, Sustainalytics), les vérifie, et les range de façon organisée et historisée, sans jamais rien écraser. EVE calcule aussi certaines données propriétaires de BDF Gestion (notes ESG, controverses) ; les indicateurs financiers, eux, restent calculés en aval par DEMAIN. JUMP et l'Infocentre, les deux sources historiques, doivent être décommissionnés début 2027.

Schéma de la base EVE : les tables de données

21 flux fournisseurs organisés autour de deux référentiels pivots, Issuer et Asset. Le lien entre les deux n'est jamais une contrainte de base : il est calculé, sur isin, lei ou code_issuer_jump, d'où le trait en pointillé plutôt qu'un trait plein.

Ce que ce schéma ne montre pas, et pourquoi.
  • Les tables techniques Django (auth_user, django_migrations, django_session...) et l'authentification (users_permanenttoken) existent dans EveDev mais ne portent aucune donnée ESG : hors sujet ici.
  • Le code de cette branche nomme la table Sustainalytics sustainalytics_equity_controversy_issuer_data (avec un s) ; sur EveDev, elle s'appelle encore sustainalytic_equity_controversy_issuer_data (sans le s) : la migration de renommage n'a probablement pas encore été jouée.
  • Le contenu du dossier Vues d'EveDev reste à confirmer : rien dans le code n'en parle, ce sont probablement des vues SQL Server créées hors Django.

Un piège de vocabulaire. La colonne is_in de cet export porte soit une liste de valeurs autorisées (ex. ['Green','Amber','RED']), soit une plage numérique (ex. min 1, max 10) : c'est une règle de validation du champ. Rien à voir avec le code ISIN d'un titre financier, la coïncidence de nom est involontaire.

Schéma de la base EVE : le trajet d'une requête

Sept routes au total. Six touchent les données, dans un ordre imposé pour la construction initiale puis libre ensuite ; une septième n'est qu'un export de documentation. Source : data/api.py et users/api.py.

PARTIE 2 / 2
Avant toute route : POST /auth/login
Authentifie un compte Django (username/password) et renvoie son PermanentToken (un jeton par utilisateur, lien un-à-un avec User). Ce jeton sert de clé d'accès sur chacune des six routes ci-dessous : aucune ne s'appelle sans elle, mais aucune ne la redemande non plus une fois obtenue.
POST/insert_data/{data_key}
  1. Le data_key doit correspondre à un flux existant et connu du système, sinon rejet.
  2. integration_process_id (l'identifiant du lot envoyé) doit être unique et supérieur à tous les précédents pour ce flux, sinon la demande est refusée.
  3. Lecture du fichier envoyé : CSV ou parquet uniquement ; tout le reste, y compris xlsx, est refusé.
  4. Nettoyage puis validation complète du contrat de données ; toute ligne qui ne respecte pas ce contrat fait échouer l'appel entier, rien n'est inséré à moitié.
  5. Insertion en base : un nouveau lot, identifié par ce integration_process_id. Rien n'écrase les lots précédents.
  6. Un rapport de qualité est calculé tout de suite sur ce nouveau lot et renvoyé en réponse, en xlsx (pas un simple message de succès).
Cette même route sert pour les 21 flux : seul le data_key change.
↓
POST/build_referential/issuer
  1. Appelable une fois jump_issuer_data et bdfg_issuer_data en base (les deux s'insèrent en parallèle par la route au-dessus).
  2. Reconstruit tout le référentiel Issuer à partir de JUMP, de BDFG et de sa propre version précédente : ce n'est jamais un ajout, toujours un recalcul complet.
  3. Référentiel vide -> réponse succès immédiate, rien d'inséré.
  4. Sinon, validation complète puis insertion : pour un référentiel, seule la date de construction identifie la version, pas de numéro de lot.
↓
POST/insert_data/jump_asset_data
  1. Même mécanique que la première route. Doit passer avant l'étape suivante : le référentiel Asset a besoin de JUMP comme source technique primaire.
↓
POST/build_referential/asset
  1. Identité d'un actif : c'est l'identifiant JUMP qui fait foi, pas le code ISIN, car un même actif peut être coté sur plusieurs places ; le code ISIN reste informatif.
  2. Enrichissement en couches : JUMP (technique) puis BDFG (correction fonctionnelle) puis le référentiel Issuer déjà construit.
  3. Même règle de remplacement complet que pour Issuer, sans numéro de lot non plus.
↓
POST/insert_data/{les 19 autres flux}
  1. Toujours la même route, la même mécanique que la première : c'est seulement à partir d'ici que l'ordre entre flux n'est plus imposé par le code.
Ensuite, à la demande, dans n'importe quel ordre
GET/export/last/{data_key}
  1. Un flux inconnu est refusé. Les colonnes demandées en option sont aussi vérifiées : une colonne qui n'existe pas fait refuser la demande.
  2. Lit le dernier lot seulement, filtré et limité directement en base, avant tout traitement supplémentaire.
  3. Par défaut, rapproche avec le référentiel avant de répondre (apply_referential_matching, désactivable).
  4. Réponse JSON, streamée. Aucun calcul financier : ce qui est stocké, tel quel.
GET/export/demain/{data_key}
  1. demain_effect_date par défaut aujourd'hui ; date_eve_import_max optionnel restreint aux lots importés à cette date ou avant.
  2. Construit le jeu DEMAIN selon une règle propre à chaque flux : si le flux ne prévoit pas ce calcul, la demande est refusée (tous les flux ne le prévoient pas).
  3. Dépivote le résultat en lignes date_effect, source, issuer_id, variable, value : un format long, différent du format large stocké en base.
  4. Réponse JSON, streamée.
POST/build/proprietary/{data_key}
  1. Calcule un jeu propriétaire BDFG pour ce data_key ; vide -> succès immédiat, rien d'inséré.
  2. Le code ne vérifie pas encore que le flux demandé est bien un flux propriétaire : un point de vigilance connu, laissé en l'état pour l'instant. Un flux qui ne prévoit pas ce calcul est refusé au moment de l'exécuter, pas avant.
  3. Sinon, validation puis insertion d'un nouveau lot, avec l'identifiant fourni par l'appelant.
GET/data_quality_assessment_report/{data_key}
  1. Un flux inconnu est refusé.
  2. Calcule le rapport qualité sur le dernier lot en base, sans paramètre pour en choisir un autre.
  3. Réponse en xlsx. Ne modifie rien en base : c'est une lecture seule, contrairement au même calcul lancé automatiquement dans /insert_data.
Une septième route, à part : GET /issuer_schemas_xlsx exporte la définition de tous les schémas issuer (un onglet par flux, jamais les flux actifs ni les référentiels) en un classeur Excel. 18 onglets, 623 champs au total, avec pour chacun son alias source, sa nullabilité, ses valeurs ou plage autorisées, et ses métadonnées (DEMAIN, qualité, controverse propriétaire). Un outil d'introspection pour explorer les contraintes de chaque flux, pas une route de données. Détail complet dans la partie 1.
